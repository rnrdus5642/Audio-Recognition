# 악기 동작 표현 수정·검증 — 2026-09-07

## 결론

아동용 정답 데이터의 누락 표현 6개를 추가하고, 다른 동작을 잘못 통과시키는
경우를 막는 비교 규칙을 Python 웹과 Unity C#에 반영했다.
**실제 아동 녹음의 정답 확정은 여전히 2/7이다. 음향 인식 문제는 미해결이며,
발표에 바로 써도 된다는 검증 결과가 아니다.**

기존 부분열 채점·점수·임계값·정렬·확정 정책은 유지했다. 모델 가중치, 출력 어휘,
혼동행렬, 오디오 입력 처리, 디코더를 바꾸거나 추가 학습하지 않았다.

## 1. 정답 등록과 호출

9단계에서 반복되는 표현을 합치면 아래 5개 동작, 10개 표현이다.
아동 카탈로그는 29개에서 35개로 늘었다.

| 동작 그룹 | 허용 표현 | 기존 녹음으로 확인한 정답 확정 |
|---|---|---|
| `lift` | 들어 / 들기 | 들어 0/2, 들기 녹음 없음 |
| `strike` | 쳐 / 치기 | 쳐 0/2, 치기 녹음 없음 |
| `put_down` | 놓아 / 놓기 | 두 표현 모두 녹음 없음 |
| `shake` | 흔들어 / 흔들기 | 흔들어 2/2, 흔들기 녹음 없음 |
| `drum` | 두드려 / 두드리기 | 두드려 0/1, 두드리기 녹음 없음 |

추가한 표현은 **들기·치기·놓아·놓기·흔들기·두드리기**다.
10개 표현의 글자는 현재 아동 모델의 출력 어휘로 표현 가능하다.
`놔`·`놔요`를 `놓아`의 허용 답으로 자동 추가하지 않았다.

웹에서는 아동 모델 + `ko_child_v2.json` + `targets_child.json`을 함께 사용한다.
정답 입력은 `들어, 들기`처럼 쉼표 또는 줄바꿈으로 구분한다.
표의 `/`는 두 표현을 나열하는 문서 표기이지 웹 입력 구분자가 아니다.

Unity의 `Begin`에는 지금 단계에서 허용할 표현만 기존 방식으로 전달한다.
전달하지 않은 표현을 자동 정답 후보로 추가하지 않으며, 새 필수 인자도 없다.
배포 카탈로그로 다섯 쌍과 열 개 단독 표현 모두 세션 시작이 가능한 것을 확인했다.

## 2. 다른 동작으로 인한 오통과 보호

예를 들어 `흔들기`의 뒤에는 `들기` 소리가 들어 있다. 기존 부분열 채점은
합성 정답 IPA `흔들기`를 `들기`로 0.997점 처리해 0.875 임계값을 넘겼다.

수정된 판정 순서는 다음과 같다.

1. 기존 방식으로 후보 하나를 고른다. 점수·임계값·음소 정렬은 변경하지 않는다.
2. 통과 후보에 동작 비교 정보가 있으면, 인식한 **전체 음소열**을 비교한다.
3. 선택된 후보와 같은 동작의 표현 중 가장 높은 전체 비교 점수를 기준으로 삼는다.
   호출에서 허용하지 않은 같은 동작의 표현도 비교 기준에만 포함한다.
4. 호출에서 허용한 동작들을 제외한 다른 동작이 그 기준보다 **엄격하게 높으면**
   통과를 취소한다. 점수가 같으면 취소하지 않는다.
5. 취소한 프레임은 연속 확인이나 보정 근거가 있는 1회 정확 일치 확정에도 쓰지 않는다.
   다른 후보로 다시 순위를 매기거나 경쟁 동작을 대신 정답 처리하지 않는다.

코드에 악기 단어를 하드코딩하지 않았다. `shared/words.csv`의 선택 필드
`action_group`으로 그룹을 선언하고, 빌드가 그룹이 있는 10개 표현 전체를 각 답의
`contrastive_alternatives`에 넣는다. 이 정보가 없는 기존 카탈로그는 기존 판정이다.
호출에서 허용한 후보와 IPA가 같은 경쟁 표현도 취소 근거에서 제외한다.

비교 정보의 잘못된 자료형·누락된 그룹·빈 음소 토큰은 양쪽에서 오류로 거부한다.
미지정/null은 기존 데이터로 취급한다. 올바른 그룹과 함께 있는 빈 배열은
비교 대상이 없는 것으로 양쪽 모두 허용한다. 현재 배포된 10개 표현은 모두
빈 배열이 아니라 동일한 10개 비교 표현을 갖는다.

### 결과 API

| Python `MatchResult` | Unity `FrameScore.Best` | 의미 |
|---|---|---|
| `competitor_rejected` | `CompetitorRejected` | 다른 동작 때문에 통과를 취소했는가 |
| `competitor_reason` | `CompetitorReason` | `other_action_scored_higher` |
| `competitor_text` | `CompetitorText` | 전체 발화에 더 잘 맞은 경쟁 표현 |
| `competitor_score` | `CompetitorScore` | 경쟁 표현의 전체 비교 점수 |
| `accepted_whole_score` | `AcceptedWholeScore` | 선택된 후보의 동작 그룹 내 최고 전체 비교 점수 |

취소되지 않은 프레임에서는 취소 정보가 비어 있다. 두 전체 비교 점수는 확률이나
임계값 판정에 쓰인 원래 `Score`가 아니다. 웹은 경쟁 표현과 비교 점수를 쉬운
한글 설명으로 표시하고 HTML을 이스케이프한다.

**클라이언트는 `Passed`·`Confirmed`·확정 이벤트를 사용해야 한다.**
취소 후에도 `Score >= Threshold`일 수 있으므로 점수만 직접 비교하면 보호 규칙을
우회한다. `Begin`/`Push`/확정 이벤트의 기존 호출 방식과 확정 발음 피드백 형식은 그대로다.

## 3. 임계값 보존

기존 29개 답의 비교 정보 외 필드, 순서, 임계값 및 보정 정책을 보존했다.
기존 1회 정확 일치 승인 28개도 유지했다. 신규 6개는 승인 없이 연속 2회가 필요하다.

| 신규 표현 | 임계값 | 기준 음성에서의 오확정 수 | 10초당 오확정 사건 수 |
|---|---:|---:|---:|
| 들기 | 0.875 | 4 | 0.001234 |
| 치기 | 0.875 | 12 | 0.003703 |
| 놓아 | 0.800 | 11 | 0.003394 |
| 놓기 | 1.000 | 0 | 0 |
| 흔들기 | 0.775 | 27 | 0.008331 |

기준은 기존 부분열 채점, 연속 2회, 연속 음성 4,998건/32,410.112초,
예산 10초당 오확정 0.01건이다. 앞선 웹 동적 생성에서 사용한 같은 측정값을
배포 데이터에 넣었다. 낮은 임계값이나 전체열 채점용 측정값으로 대체하지 않았다.

이는 실제 아동의 해당 단어 검출률이나 세션별 오정답 확률 1%를 보장하지 않는다.
특히 `놓기`의 1.0 임계값은 실제 녹음으로 통과 가능성을 확인하지 못했다.

## 4. 실제 음성과 교차 검증

로컬 라벨링 83개 클립에서 기존 아동 모델로 403개 창을 추론한 불변 캐시를 사용했다.
입력은 16kHz 모노, 40,000샘플 창, 8,000샘플 hop이며 클립 끝의 hop 정렬과
1초 무음 꼬리를 동일하게 적용했다. 단어별 유리한 구간 선택이나 증폭은 하지 않았다.
비교 기준은 수정 전 웹이 생성한 같은 10개 표현·임계값의 고정 카탈로그다.

83클립 × 5동작 = 415회 중 정답 7회, 다른 동작 390회, 관련 변형 등으로
오답이라고 단정하기 어려워 제외한 18회다. 사람이 발음을 검수한 라벨은 아니므로
의도한 단어와 실제 발음이 정확히 같다고 가정하지 않는다.

| 검사 | 수정 전 | 수정 후 |
|---|---:|---:|
| 정답 표현 녹음 확정 | 2/7 | 2/7 |
| 다른 동작에서의 잘못된 확정 | 2/390 | 1/390 |
| 정답 IPA 합성 입력의 자기 동작 확정 | 10/10 | 10/10 |
| 정답 IPA 합성 입력의 다른 동작 오확정 | 1/40 | 0/40 |

이번 표본에서 새 오확정·기존 정답 손실은 없었다. 남은 실제 오확정 1건은
해결하지 못했다. 미통과 정답 녹음 5개는 모두 **통과 프레임 자체가 없어서**,
단순히 연속 2회 요구를 완화하는 것으로 해결되지 않는다.

실제 웹 `live_step`을 7개 정답 클립으로 실행해 캐시와 26개 입력 창의 해시가
일치함을 확인했다. 14/14개 정답 후보에 비교 정보가 전달됐고, 합성 오통과 입력의
취소 설명·점수·미확정 상태도 실제 콜백에서 확인했다. 브라우저의 육안 검사는 아니다.

Unity 패키지의 실제 `PronunciationSession`에는 캐시 인식기를 주입해 총 447케이스
(실음성 판정 397 + 합성 50), 2,095프레임을 Python과 비교했다. 후보·원점수·임계값·
통과·연속 횟수·확정·취소 정보 모두 차이 0건이었다. 확정 13건의 피드백도 확인했다.
이 13건은 합성·교차 시험을 포함한 수이며 실제 아동 정답 13건을 뜻하지 않는다.

## 5. 시험했지만 반영하지 않은 방법

- **전체열 채점으로 전환:** 실제 7개에서는 2→3개가 통과했지만, 합성 입력에서
  반대로 `들기`를 `흔들기`로 통과시키는 새 오정답이 생겨 폐기했다.
- **임계값 하향:** 탐색값으로 5/7까지 나왔으나, 연속 문장 음성으로 얻은 낮은
  임계값이 단독 오답 단어를 안전하게 구별한다는 근거가 없어 반영하지 않았다.
- **발화 구간만 정규화·배치 변경:** 시험한 입력 변형 두 가지 모두 2/7로 개선 없음.
- **패딩/마스크/가변 길이 분리 실험:** 해당 7개에서 회복을 확인하지 못했다.
  같은 프레임을 반복한 진단 결과를 실제 연속 청취 성공으로 계산하지 않았다.
- **언어모델 없는 CTC 빔 탐색:** 32개 창에서 기존 greedy와 최종 토큰열이 같았고
  확정도 2/7로 같았다. 모델 출력이나 디코더는 교체하지 않았다.

이 결과는 **시험한 방법이 해당 7개에 효과가 없었다**는 뜻이다. 입력 처리 문제가
모두 배제됐다거나 모델만이 유일한 원인이라고 증명한 것은 아니다.

## 6. Unity 적용과 다음 작업

다음 세 아동 카탈로그는 동일하다.

- `shared/targets_child.json` — 웹에서 쓰는 생성물.
- `unity/Assets/StreamingAssets/targets_child.json` — 이 저장소의 Unity 데이터.
- `unity/Packages/com.domicube.phoneme-matching/Samples~/KoreanData/targets_child.json` — 패키지 샘플.

다른 프로젝트에는 **패키지와 아동 정답 데이터를 함께 갱신**해야 한다.
패키지만 갱신해도 이미 복사한 `StreamingAssets/targets_child.json`은 바뀌지 않는다.
`Tools > Phoneme Matching > 데이터 파일 설치`로 갱신하되 사용자 수정 데이터는
먼저 보관한다. `정답 데이터 다시 만들기`는 성인 `targets.json`용이므로 대신 쓰지 않는다.

아동 데이터의 저장소 내 재생성 명령은 다음과 같다. Unity 복사본도 함께 갱신해야 한다.

```powershell
python -m python.build.build_targets --matrix-id ko_child_v2 --thresholds shared/thresholds_child.json --output shared/targets_child.json --strict
```

성인 `shared/targets.json`은 기존 29개 그대로다. 신규 6개에 성인 보정 근거가
없어 이번에 재생성하지 않았으며, 아동용 개선을 성인에도 적용했다고 주장하지 않는다.

남은 우선순위는 실제 미통과 5개를 사람이 들어 라벨/발음을 확인하고, 녹음이 없는
6개 표현과 혼동하기 쉬운 오답 발화를 확보한 뒤 음향 인식·단어별 보정을 다시
검증하는 것이다. 현재 소수 표본을 외워 통과시키거나 검수되지 않은 의도 라벨로
추가 학습하지 않았다. 외부 Unity 프로젝트 수정, 커밋·푸시는 이 턴에 하지 않았다.
