# 한국어 자모 학습 출발점의 Windows / Unity 실측 결과

검증일: 2026-09-14. **대상은 Windows PC의 한국어 아동 인식이며, Unity GPUCompute로 실행할 수 있어야 한다.**

**권고: 한국어 HuBERT 계열로 재출발한다. Unity 6 / Inference Engine 2.6.1을 사용한다면 `team-lucid/hubert-xlarge-korean` + 자모 CTC를 1순위로, Unity 2022.3 / Sentis 1.2.0-exp.2를 유지한다면 검증을 통과한 `team-lucid/hubert-large-korean` + 자모 CTC를 선택한다.** XLarge의 구형 엔진 출력 차이를 해결하지 않은 상태에서 두 환경에 같은 배포 결과를 약속하면 안 된다.

11개 공개 사전학습 인코더에 같은 자모 출력층을 학습해 기본 비교했고, 주요 6개에는 같은 아동 자료로 400 update의 본체 학습도 수행했다. 모든 기본 인코더를 실제 Windows Unity 6 실행 파일에서 시험했다. 이 권고는 **본 학습을 시작할 기반 선택**에 관한 것이며 완성된 인식기·발음 오류 안내 제품의 승인 결과는 아니다.

| 사용할 엔진 | 권장 출발점 | 아동 test JER | 학습한 가중치의 GPU 확인 |
|---|---|---:|---|
| Unity 6 / Inference Engine 2.6.1 | 한국어 HuBERT XLarge, 약 962M | **11.24%** | 12개 수치 대조 입력 × 3회와 보유 녹음의 106개 고정 창에서 CTC 일치 |
| Unity 2022.3 / Sentis 1.2.0-exp.2 | 한국어 HuBERT Large, 약 315M | **14.43%** | 해당 엔진의 12개 수치 대조 입력에서 CTC 일치 |

모델 출처: [한국어 HuBERT XLarge](https://huggingface.co/team-lucid/hubert-xlarge-korean), [한국어 HuBERT Large](https://huggingface.co/team-lucid/hubert-large-korean). 두 공개 모델은 사전학습 인코더이며 자모 CTC 출력층은 이번 실험에서 추가했다.

## 선택 근거

동일한 아동 평가 음성 600개에서 XLarge의 JER는 11.24%, Large는 14.43%였다. XLarge가 **3.20%p 낮았고**, 같은 평가 화자 149명을 단위로 계산한 탐색적 95% 구간은 **−3.85~−2.56%p**였다. 5·6·7세 그룹과 잡음 메타데이터 유무별 그룹에서도 XLarge의 점수가 낮았다. 다만 XLarge의 본체 학습 seed는 한 개이며, 서로 다른 사전학습 이력까지 통제한 순수한 모델 크기 효과 실험은 아니다.

Large를 다른 학습 순서와 dropout seed로 다시 학습한 결과는 JER 14.47%였다. 초기 출력층은 동일하게 사용했다. 이는 Large의 이번 짧은 학습 결과가 한 번의 학습 순서에만 의존하지 않았다는 보조 근거다.

실측 PC는 **Windows 11 / RTX 5060 Ti 16GB / Ryzen 7 7800X3D / RAM 약 64GiB**다. 학습한 XLarge의 Unity 6 추론은 2.5초 입력 한 번당 warm p95 **69.26~69.31ms**, 프로세스의 GPU local 사용량은 약 **3.64GiB**였다. 세 번의 독립 실행에서 CTC 차이는 없었고, 최대 logit 절대 오차는 약 0.00261이었다. 따라서 현재 PC에서는 크기만을 이유로 1B급을 제외할 필요가 없다. 실제 게임의 60FPS·다른 GPU·IL2CPP까지 검증한 결과는 아니다.

이번 XLarge 학습의 PyTorch 최대 GPU 할당은 **12.94GiB**, Large는 **5.33GiB**였다. XLarge에는 앞 24개 인코더 층의 AdamW 상태·갱신을 CPU에 두는 방식을 사용했다. 검증 등을 포함한 경과 시간은 각각 약 20.1분과 7.3분이며, 순수 학습 처리량 비교로 쓰지 않는다. GPU 추론 가능성과 학습 자원 요구량을 구분해야 한다.

## 실제로 확인된 적용 제약

- **XLarge / 구형 엔진:** 학습한 동일 가중치를 Unity 2022.3 / Sentis 1.2에 넣으면 12개 입력 중 CTC 일치는 4개뿐이었다. 1,488 frame 중 39개가 달랐고 최대 logit 절대 오차는 10.72였다. 실행 자체는 됐지만 적용 검증은 실패다. 원인이 수치 연산·변환·구형 런타임 중 어디에 있는지는 이번 실험에서 확정하지 않았다. 모든 Unity 2022 배포 방법이 불가능하다는 뜻도 아니다. 같은 가중치는 Unity 6에서 통과했다.
- **W2v-BERT:** 추가 학습 후 JER 14.89%로 Large와 가까웠다. 두 모델의 test 차이에 대한 탐색적 구간은 0을 포함해 전사 성능만으로 확실한 우열을 말하기 어렵다. 그러나 원본 Unity 6 그래프는 CTC 6/12 일치, 최대 절대 오차 4.93이었고 Unity 2022에서는 실행 오류가 났다. 고정 크기 연산을 미리 계산한 보완 그래프도 Unity에서 실패했다. 이 후보는 현재 변환 방식으로 배포하기 위한 추가 작업이 필요하다.
- **다른 후보:** 같은 400 update에서 XLS-R 300M은 34.51%, OmniASR W2V 300M은 25.26%, WavLM Large는 29.11% JER였다. 나머지 5개에는 출력층 학습과 Unity 기본 검사만 했으며, 본체 학습을 하지 않은 후보의 최종 잠재 성능까지 낮다고 단정하지 않는다. MMS/XEUS의 이용 조건과 WavLM의 가중치 라이선스 확인 사항도 별도로 남겼다.
- **‘놔’와 단어 성능:** 원래 길이 그대로 평가한 보유 녹음에서 XLarge의 `놔`는 1/4, `내려놔`는 4/4, `잡아`는 8/11이었다. Large는 각각 0/4, 0/4, 9/11이었다. 따라서 XLarge가 모든 단어에서 우세하거나 짧은 단어 문제가 끝났다는 결론은 아니다. 단음절·희귀 발음 조합을 포함한 충분한 본 학습이 필요하다.

고정 길이의 실제 Unity 6 검사에서도 위치에 따른 차이가 있었다. 53개 녹음을 가운데에 넣으면 XLarge 36/53, Large 33/53이 완전히 일치했고, 끝쪽에 넣으면 각각 34/53, 36/53이었다. 각 모델의 두 위치 106개 입력은 모두 Python과 같은 CTC 결과였다. 전사 결과의 변환은 일치하지만 발화 위치·단어별 인식 성능은 별도 문제이며, 이 53개만으로 아동 전체나 서비스 오확정률을 대표할 수 없다.

**다음 구현은 선정 인코더의 자모 본 학습, 자모 디코더 연결, 새 모델 기준 임계값·혼동 행렬 보정이다.** 현재 Python/Unity 디코더는 완성형 한글만 남기는 부분이 있어 자모 모델 파일만 교체하면 출력이 제거될 수 있다. 발음 오류 안내는 실제 발음에 대한 별도 정오 라벨로 검증해야 한다.

아래 표의 JER는 낮을수록 좋다. ‘고정 본체’는 원래/스칼라 보정 특징 × 두 학습률의 네 조건 중 valid로 선택한 출력층이다. Unity 6 기본 표의 속도·CTC 대조는 원래 출력층 그래프이며, 학습한 최종 후보의 결과는 별도 반복 검사 표에 있다. **CTC 일치와 모든 수치 허용 오차의 충족은 같은 항목이 아니다.** XLS-R 1B는 원본 Unity 최대 절대 오차가 약 0.0676으로 초기 0.02 기준을 넘었고, 일부 후보는 CPU ONNX 비교에서도 초기 기준을 넘었다. 상세 값은 집계 JSON에 보존했다.

## 무엇을 확인한 실험인가

목표는 **Windows PC에서 한국어 아동 음성을 자모로 인식하고, Unity GPU로 실행할 새 학습 출발점**을 고르는 것이다. 한국어 학습 완료 ASR 모델 64개를 비교한 이전 조사와 달리, 이번에는 공개 사전학습 인코더 11개 위에 동일한 한국어 자모 CTC 출력층을 새로 학습했다. 공개 인코더 자체가 이미 한국어 자모를 출력하는 완성품이라는 뜻은 아니다.

모델 이름의 300M/600M/1B는 공개 명칭이다. 표의 규모는 이 실험에서 실제로 로드한 인코더의 파라미터 수이며, 사전학습 손실 전용 양자화기 등의 크기를 제외한다. Miniijune V2처럼 이미 아동 ASR 학습을 거친 모델은 이번 새 사전학습 인코더 비교와 구분했다. 이전 결과의 PER·단어 정확도와 이번 JER를 직접 비교하지 않는다.

## 평가 자료와 자모 정의

| 분할 | 녹음 수 | 화자 수 | 길이 |
|---|---:|---:|---:|
| 학습 | 5,999 | 682 | 7.544시간 |
| 검증(valid) | 600 | 144 | 0.739시간 |
| 평가(test) | 600 | 149 | 0.756시간 |

보유 AI Hub 아동 원본 자료에서 화자를 먼저 분리하고, 5·6·7세를 거의 동일하게 추출했다. 학습은 화자당 최대 16개, 검증·평가는 최대 8개다. 모델 점수를 보기 전에 파일명 SHA 기반 순서를 고정했다. 분할 사이 화자·PCM 중복은 0건이다. 손상 WAV 한 개는 모든 모델에서 동일하게 제외했고 점수를 보고 대체하지 않았다.

1~6.5초, 한글 2~45음절인 표본이다. 따라서 **‘놔’, ‘쳐’만 독립적으로 말하는 자료가 학습 표본에 충분히 반영된 설계가 아니다.** 학습 문장 중 ‘놔’라는 글자가 있는 파일은 두 개이며, 이 표본의 좋은 문장 점수만으로 단음절 인식을 보장할 수 없다. test는 정형 발화 505개·자유 발화 95개, 잡음 메타데이터가 있는 음성 150개·없는 음성 450개다. 공개 사전학습 자료와 우리 평가 자료의 모든 파일·화자 중복까지 배제한 것은 아니다.

프로젝트의 발음 규칙을 전사 문장에 적용하고 자모로 분해했다. 자모 40개, 단어 경계, CTC blank를 합쳐 42개 출력이다. 학습 표본에 40개 자모가 모두 있지만 빈도는 불균형하며, `ㅞ`는 6회·`ㅒ`는 16회뿐이다. 발음 규칙 뒤 `샅/삳`은 같은 자모열, `잡아/자바`도 같은 자모열이 된다. `놔/와`, `잡아/작아`는 구별된다. 이 동일 발음 처리는 발음 문맥을 고려한 라벨 규칙으로 다루며, 철자를 모든 문맥에서 일괄 치환하지 않는다.

JER = 자모의 삽입·삭제·대치 수 / 정답 자모 수다. 낮을수록 좋다. 경계 기호는 점수에서 제외하지만 무음 초성 `ㅇ`은 남아 있어 엄밀한 IPA 음소 오류율(PER)과 다르다. 사람의 실제 잘못된 발음을 듣고 붙인 라벨도 아니다. 그러므로 `100 - JER`를 단어 정답률로 부르거나 이 점수로 발음 오류 안내의 정확성을 주장하지 않는다.

## 같은 조건으로 비교한 범위

1. 인코더를 고정하고 마지막 층의 특징을 FP32로 추출했다. 캐시는 FP16이며, 모든 모델에 같은 선형 CTC 출력층 학습 예산을 주었다. 조건당 1,600 update, batch 32, seed 917, AdamW다.
2. 인코더 출력의 크기가 크게 달라 원래 특징과 단일 스칼라로 크기만 맞춘 특징을 모두 시험했다. 스칼라는 학습 음성에서만 구했으며 채널 간 상대 크기와 중심은 바꾸지 않았다. 원래/보정 특징 × 학습률 0.001/0.003, 네 조건의 valid JER로 출력층을 골랐다. test나 보유 단어 점수로 조건을 선택하지 않았다.
3. 주요 다섯 후보와 한국어 HuBERT XLarge에는 본체 학습도 적용했다. 같은 순서로 학습 발화 8개를 누적해 400번 갱신했다. 실제 본체 갱신에 쓰인 발화 노출은 3,200회다. 파형 인코더의 입력 CNN은 고정하고 나머지 인코더와 출력층을 학습했다. W2v-BERT의 Conformer 블록은 학습 대상이다. encoder LR 2e-5, head LR 1e-4, warmup 40, 선형 감소, gradient clip 1, BF16 학습/FP32 평가다. time/feature masking과 layerdrop은 끄고 나머지는 모델의 기본 dropout을 유지했다.
4. 100 update마다 valid를 평가해 checkpoint를 선택하고 test를 평가했다. 대표 한 모델은 본체 학습 seed 918도 확인했다. 이때도 같은 초기 출력층을 사용하므로 전체 파이프라인을 독립적으로 두 번 학습한 결과는 아니다.

한국어 1B 학습에서는 48개 인코더 층 중 앞 24개 층의 AdamW 상태·가중치 갱신을 CPU에 두어 16GB GPU의 메모리 부담을 낮췄다. 인코더 가중치와 순전파·역전파는 GPU에 있다. 같은 FP32 AdamW 수식을 유지하며, 분할 갱신 로직은 일반 AdamW와 12 update 대조에서 최대 파라미터 차이가 0이었다. 이 대조는 CPU상의 갱신 로직 검사이며 GPU/CPU 간 모든 연산의 bitwise 일치를 증명한 것은 아니다. 배포 추론의 CPU fallback 여부와도 구분한다.

처음 시도한 채널별 평균·분산 보정은 한국어 HuBERT의 valid 성능을 악화시켰다. 이 보정과 그 출력층에서 시작했다가 중단한 본체 학습은 주 비교에서 제외하고 원본 로그를 `experiments/per-channel-head/`에 보존했다. 이후 모든 모델에 동일하게 적용한 보정은 **단일 스칼라**다. 원래 특징의 좋은 결과도 valid 선택 후보에 계속 포함했다.

이는 **동일한 짧은 적응 예산에서의 결과**다. 마지막 층 선형 출력층의 점수는 모델의 잠재 성능 상한이 아니고, 본체 400 update도 충분히 수렴한 학습이 아니다. 전체 데이터·모델별 학습률·중간 층 선택을 모두 탐색한 최종 성능 순위로 해석하지 않는다. 통계 구간도 같은 test 화자 149명을 복원 추출한 탐색적 비교로, 다중 모델 선택이나 사전학습 중복·모든 학습 seed의 불확실성을 해소하지 않는다.

## Windows Unity GPU 검사 방법

실측 장비는 Windows 11, Ryzen 7 7800X3D, RAM 약 64GiB, **RTX 5060 Ti 16GB**다. Unity 6000.3.18f1 / Inference Engine 2.6.1과 Unity 2022.3.62f2 / Sentis 1.2.0-exp.2의 독립 프로젝트를 Windows x64 Mono 실행 파일로 빌드했다. 실제 게임 프로젝트나 실행 중인 다른 Unity 프로젝트는 변경하지 않았다.

진단 실행 파일은 지정한 외부 `.sentis` 파일과 고정 입력을 로드하는 방식이다. 제품 빌드에 모델을 포함하고 설치·업데이트까지 검증한 배포본은 아니다.

FP32 ONNX(opset 17)에 파형 전처리와 CTC 출력층까지 포함했다. 입력은 16kHz mono 2.5초(40,000 sample)로 고정했다. 실제 Windows Player / Direct3D 11 / GPUCompute에서 결과를 CPU로 읽어 올 때까지 기다려 시간을 측정했다. 4회 warmup 이후 40회 지연의 중앙값과 p95를 기록했다. 최종 학습 후보는 새 가중치를 다시 내보내고 독립 실행을 반복했다. 단순히 `GPUCompute`를 지정하는 데 그치지 않고 Worker의 실제 backend와 CPU fallback 할당도 확인했다.

정식 Unity 지연 측정 때 다른 실험의 GPU 작업은 겹치지 않게 했다. 다만 독립적인 작은 출력층 실험과 일부 GPU 기능 검사는 본체 학습과 병행했다. 학습 경과 시간은 검증·파일 저장·보유 단어 검사와 일부 CPU 진단도 포함하므로 모델별 순수 학습 처리량 비교로 쓰지 않는다.

Unity의 12개 대조 입력은 test 음성 8개의 2.5초 창과 gain 감소·잡음 추가·무음·잡음만 있는 입력이다. 문장 전체 인식 성능 평가용이 아니라 **동일 입력에 대한 Python/ONNX/Unity 출력 일치 검사**다. CTC 일치 외에 모든 logit의 절대 오차·RMSE도 기록했다. Python/ONNX 초기 절대오차 0.02 기준을 넘은 결과는 숨기지 않는다. 일부 비교의 CTC가 같더라도 수치 기준까지 모두 통과했다는 뜻은 아니다.

기존 0.5초 hop을 따라가기 위한 필요조건은 p95 500ms 미만이다. **22ms나 70ms의 동기 추론이 게임의 60FPS 프레임 예산을 만족한다는 뜻은 아니다.** 실제 장면에서 비동기 결과 읽기·스케줄링과 GPU 렌더링 경합을 확인해야 한다. 첫 호출·모델 로딩 비용도 별도로 기록했다. 다른 GPU·16GiB RAM PC·IL2CPP·Direct3D 12는 이번 실측 대상이 아니다.

메모리는 Windows `GetProcessMemoryInfo`와 DXGI `QueryVideoMemoryInfo`로 측정했다. GPU local은 쿼리 시점의 해당 프로세스 사용량이며 순간 최대 VRAM이나 최소 GPU 사양은 아니다. Unity Profiler/Mono API가 0을 반환한 조기 기록은 사용량 0으로 해석하지 않았다. [Windows 프로세스 메모리](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex), [DXGI 메모리 조회](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_4/nf-dxgi1_4-idxgiadapter3-queryvideomemoryinfo).

## 보유 악기놀이 녹음이 의미하는 범위

보유 녹음은 총 53개다. 사용자 성인 음성 7개(`잡아` 5개/`작아` 2개)와 두 화자의 악기놀이 46개이며, 뒤의 두 화자는 나이를 확인하지 못했으므로 아동 표본으로 세지 않았다. 파일 SHA를 이전 평가 목록과 대조했다. 원본, 앞뒤 각 1초 무음, 백색잡음 20dB/10dB를 검사했다. 212개 파생 입력을 212명의 독립 표본으로 세지 않는다.

녹음 전체의 greedy CTC 출력과 기준 자모열을 비교했다. 목표 단어 강제, 임시 별칭, 정답 임계값, 2회 연속 판정 보정은 쓰지 않았다. 표의 완전 일치는 제품의 실제 정답 통과율과 다르다. `ㅐ/ㅔ`, `ㅒ/ㅖ`를 합친 민감도 점수도 별도 JSON에 보존했다. 잡음은 실제 방 소음이 아닌 통제된 백색잡음이다. 제품 오확정률·발음 오류 잘못 지적률을 대표할 충분한 음성/비음성 음수 표본은 이번 실험에 없다.

최종 후보는 이 53개 녹음을 실제 Unity GPU에서도 추가 검사했다. 녹음 길이는 0.704~2.460초라 발화를 자르지 않고 2.5초 창에 넣을 수 있었다. 가운데 배치와 끝쪽 배치(가능한 경우 뒤에 0.1초 여백), 두 위치의 106개 파생 입력을 모델마다 검사했다. 이는 고정 입력에서의 전사·변환 일치 검사이며 마이크·VAD·게임 전체를 연결한 제품 평가와는 구분한다.

## 모델 출처와 적용 조건

한국어 HuBERT Large는 공개 카드상 AI Hub의 자유대화 음성(일반남여)·다화자 음성합성·방송 대화 자료에서 약 4,000시간을 사용했다. 한국어 아동 ASR로 학습된 Miniijune V2와는 다른 출발점이다. 카드의 예제 출력 차원 등 오기는 실제 config와 가중치로 확인했다. XLarge는 실제 48층·1280차원 가중치가 공개돼 있지만, 카드가 Base/Large 설명을 반복해 XLarge 고유 학습 이력은 충분하지 않다. 두 모델 카드의 라이선스는 Apache-2.0이다. [Large 카드](https://huggingface.co/team-lucid/hubert-large-korean), [XLarge 카드](https://huggingface.co/team-lucid/hubert-xlarge-korean).

OmniASR은 Meta의 공개 W2V SSL 인코더를 변환했다. 가중치 이름과 전처리 epsilon을 확인하고 독립 PyTorch 수식과 대조했지만, Windows에서 공식 fairseq2 런타임까지 실행한 대조는 아니다. XEUS는 ESPnet 인코더 가중치를 엄격히 로드하고, 공개 SSL 사용 방식에 맞게 마지막 블록의 추가 ASR 정규화 전 표현을 사용했다. 각 어댑터 검증 기록은 결과 JSON에 포함했다. [Omnilingual 공식 저장소](https://github.com/facebookresearch/omnilingual-asr), [XEUS 카드](https://huggingface.co/espnet/xeus).

XLS-R과 OmniASR의 공개 조건은 Apache-2.0, W2v-BERT는 MIT다. MMS는 CC-BY-NC-4.0, XEUS는 현재 CC-BY-NC-SA-4.0이라 제품의 이용 목적과 별도 검토가 필요하다. WavLM은 HF 카드가 연결하는 UniSpeech 라이선스와 UniLM 코드 라이선스가 달라 가중치 조건을 MIT라고 단정하지 않았다. 모델 라이선스가 추가 학습 자료의 이용 조건을 대신하지 않는다. [XLS-R](https://huggingface.co/facebook/wav2vec2-xls-r-300m), [W2v-BERT](https://huggingface.co/facebook/w2v-bert-2.0), [MMS](https://huggingface.co/facebook/mms-1b), [WavLM](https://huggingface.co/microsoft/wavlm-large).

## 프로젝트를 실제로 전환할 때 필요한 작업

1. 자모/발음 라벨 정책을 먼저 확정한다. 같은 발음의 종성 중화, 연음, 초성의 무음 `ㅇ`, `ㅐ/ㅔ` 취급을 Python과 Unity에서 일치시킨다. 목표 발화 전사와 사람이 실제로 낸 발음의 오류 라벨을 구분한다.
2. 선정 인코더를 지원하는 학습 어댑터와 자모 토크나이저를 추가하고 학습 manifest를 재생성한다. 현재 `python/tools/child_finetune/train.py`는 `Wav2Vec2ForCTC`를 직접 사용하므로 모델 이름만 바꾸는 방식으로 HuBERT를 연결할 수 없다. 희귀 자모·짧은 단어와 실제 아동 발화를 충분히 포함해 본 학습한다. 새 최종 평가 화자는 튜닝에 사용하지 않는다.
3. 자모 출력용 디코더를 연결한다. 현재 Python `recognizer/ko/asr.py`의 정제 규칙과 Unity `Runtime/CtcDecoder.cs`의 `Sanitize`는 완성형 한글만 남긴다. 따라서 이번 자모 logits를 기존 패키지에 곧바로 넣으면 출력이 제거될 수 있다. 자모열을 발음 비교에 전달하는 경로와 기존 표시용 텍스트 경로를 명시적으로 설계해야 한다.
4. 최종 학습 가중치·42개 출력 정의·전처리 설정을 함께 내보낸다. 이번 독립 ONNX에는 파형 전처리가 포함돼 있으므로 기존 Unity의 외부 정규화와 중복하지 않도록 계약을 맞춘다. 실제 게임에서 마이크/VAD/창 길이·GPU 스케줄링·빌드 방식을 포함해 검사한다.
5. 목표 단어 통과율, 유사한 다른 단어의 오확정률, 무음·생활 소음 오확정을 별도로 측정한다. 기존 모델용 임계값·혼동 행렬도 새 모델 결과로 다시 보정한다. 발음 오류 안내는 전문가가 실제 발음에 붙인 라벨로 잘못 지적한 비율과 놓친 비율을 검사한다. 자모 출력 목록에서 ‘놔’를 표현할 수 있게 된 것만으로 이 검사를 대체하지 않는다.

실험 도구는 `python/tools/encoder_screen/`, 대용량 가중치·음성·ONNX·Unity 프로젝트·실행 파일·개별 결과는 `.venv/encoder-screen-0914/`에 보존한다. 저장소 문서에는 집계와 재현용 SHA만 남긴다. 이번 작업에서는 사용 중인 인식 모델이나 Unity 패키지를 교체하지 않았고, 기존 임시조치 복구 작업 및 아동 학습 도구의 편집 상태도 보존했다.
