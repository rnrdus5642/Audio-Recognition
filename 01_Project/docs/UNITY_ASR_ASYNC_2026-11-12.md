# Unity 음성 정답 처리의 프레임 지연 개선

2026-11-12, 패키지 `com.domicube.phoneme-matching` **0.9.1-preview.2**. Unity 2022.3.62f2 / Sentis 1.2.0-exp.2 / Windows D3D11 기준이다. PNG 저장 코드·설정은 사용자 요청에 따라 변경하지 않았다.

## 원인과 변경

기존 `PronunciationListener → PronunciationSession.TryPush → ObservedPhonemeRecognizer → SentisPhonemeRecognizer`는 메인 스레드에서 GPU 모델을 예약한 직후 `MakeReadable()`로 완료를 기다렸다. 이전 계측에서는 추론 약64ms 중 약59ms가 이 대기였다. 0.5초마다 같은 대기가 반복됐다. 단순히 GPU 메서드를 `Task.Run`에 넣으면 Unity 스레드 제약을 위반하므로 그렇게 처리하지 않는다.

현재 경로는 `TryAdvance → IAsyncPhonemeRecognizer.RecognizeAsync → StartManualSchedule → AsyncReadbackRequest → 완료된 창의 기존 v5 후처리`다. Unity 스레드에서 프레임마다 최대64레이어 또는 예약 시간1ms까지 예약한다. 1ms는 전체 프레임이나 개별 GPU 레이어의 상한을 보장하지 않는다. 읽기 완료 콜백에서만 `MakeReadable`을 호출한다. 한 모델의 동시 실행은 하나로 제한한다.

마이크 폴링과 문항 타임아웃은 대기 중에도 매 프레임 진행한다. 샘플 순서와 원래 오디오 시간을 유지하고 프레임당 완료 창 하나를 판정한다. 이전 질문의 지연 결과는 취소로 폐기하며 GPU 소유 자원은 완료 이후 해제한다. 큐 오버플로·추론 실패는 예외를 기록하고 청취를 중단한다. 세 게임의 기존 감시 코드가 입력 중단을 발견해 입력 오류·재시도 대기로 전환한다. 기술 오류를 아동의 시간 초과/오답으로 처리하지 않도록 `OnTimedOut`은 실제 제한 시간에만 보낸다. 세 프로젝트의 `Prepare()`는 실패한 모델을 재생성한다.

최종3에포크 모델, 2.5초 입력 창, 0.5초 hop, v5 점수·임계값·확인 횟수, 정답 단어, 씬·Timeline은 유지한다. 기존 동기 API는 호환용이며 `Warmup`과 모델 로딩은 여전히 시작 시 동기 실행한다.

## 실제 모델 측정

Music `mainroom` 고정 자세, RTX5060Ti, D3D11, 기존 NPC 음성의 처음2.5초(16kHz 모노)를 사용했다. **PNG 캡처는 활성 상태를 유지**했다. 모드마다8초, 추론 모드는 각14회. 실제 마이크·HMD는 사용하지 않았다. 프레임 시간은 Player coroutine의 `Time.unscaledDeltaTime`이다. 72fps는 Editor의 목표 프레임을 제한한 조건이며 HMD 측정이 아니다.

| 조건 | 측정 프레임 수 | 최대 프레임 | 40ms 초과 | 평균 추론 완료 지연 |
|---|---:|---:|---:|---:|
| 추론 없음 | 1,874 | 14.74ms | 0 | — |
| 기존 동기 실행 | 1,639 | 75.75ms | 14 | 64.51ms |
| 비동기·프레임 분산 | 1,800 | 43.88ms | 1 | 102.50ms |
| 비동기·72fps 제한 | 577 | 18.03ms | 0 | 291.09ms |

반복적인 긴 프레임은 줄었지만 모든 순간 멈춤이 제거됐다는 의미는 아니다. 비동기 조건의 단발43.88ms 원인은 이 계측만으로 분리하지 않았다. 화면 지연을 줄이는 대신 추론 완료 지연은 늘었다. 측정 GPU의72fps 조건에서는 평균291ms로500ms hop 이내였다. 더 느린 장치에서는 큐 누적을 별도로 확인해야 한다.

모든42회 출력은 `실로폰을 쳤어우`로 같았다. 최대 로짓 차이는 약3.25e-5로 로짓 비트 일치나 전체 데이터셋 정확도 동일성을 주장하지 않는다. 실제 GPU에서 중복 실행 거절, 취소 후 드레인·증거 폐기·재사용, 실행 중 Dispose의 지연 해제를 확인했다.

## 검증과 적용

- 세 프로젝트의 `Packages`에 같은 tgz를 저장하고 manifest/lock이 프로젝트 안의 상대 경로를 참조하도록 했다. Music/Dino/Flower의 관측 래퍼가 비동기 인터페이스를 전달한다. 별도 모델 재다운로드는 필요 없다. 기존 빌드 파일에는 재빌드가 필요하다.
- 공통 순서·세션 검사25/25 통과, Unity PlayMode 검사36/36 통과. v5의11,804개 사례·98,494회 비교를 포함한다.
- 전체 포터블 레거시 검사에서는 변경 전23실패, 변경 후 같은23실패로 신규 실패가 없었다. 전체 스위트 통과를 뜻하지 않는다.
- Music 전체 씬 QA236통과/0실패/콘솔 오류0. 최종 tgz로 Windows Player 스크립트 컴파일 통과. 완전한 Player 빌드는 수행하지 않았다.
- Flower 관련 Editor 검사60/60 통과(진행 중 입력 중단을 오답/시간 초과로 기록하지 않고 재시도를 기다리는 검사 포함). Dinosaurs 관련 Editor 검사18/18 통과, Windows Player 스크립트 컴파일을 포함한다.

측정은 0.9.1-preview.1에서 수행했고 최종 preview.2의 Sentis 추론·관측 어댑터 코드는 동일하다. 최종 수정은 실패를 시간 초과 이벤트로 전환하지 않고 기존 게임의 입력 오류 대기를 유지하는 것과 관련 검사·문서다.

## 남은 확인

Claude 최종 검수는 승인·차단 없음이다. 첫 검토의 '기술 실패에도 시간 초과 이벤트를 보낼 것'이라는 제안은 세 게임의 기존 입력 중단 감시를 추가 확인한 뒤 철회했다. 최종본은 기술 실패에 정답/시간 초과 이벤트를 보내지 않고 `IsListening == false`를 통해 기존 오류 대기 흐름을 사용한다. 직접 연결하는 소비자도 이 상태를 감시해야 한다. 관련 리스너와 게임 컨트롤러는 각각 검증했으며 실제 마이크를 통한 전 구간 통합 검증은 아니다. `IsFaulted` 모델 재생성은 코드 경로로 확인했고 실제 GPU 고장을 유발하는 검사는 수행하지 않았다.

실제 마이크·HMD에서 화면과 오디오 끊김의 개선 여부, 장시간 실행, 다른 GPU/그래픽 API, 완전한 Player 빌드는 별도 검증이 필요하다. PNG 기능은 수정하지 않았으므로 그 기능의 부하는 남는다.

GPU 장치 손실로 읽기 콜백 자체가 영구히 오지 않는 경우의 복구는 이번 범위에서 분리한다. 현재 워커는 실행 중 자원을 안전하게 유지하지만 재사용이 불가능할 수 있어 앱 재시작이 필요하다. 세 게임은 양수 문항 제한 시간을 전달하므로 해당 질문의 무한 대기는 피한다. 후속 과제는 장기 대기 경고, 고장 워커 격리 및 안전한 재생성이다. 일반 실패는 오류 콜백/예외를 통해 재시도 경로로 종료한다.
